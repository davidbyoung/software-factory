# Proposal

From [kodor-ai/kodor#130](https://github.com/kodor-ai/kodor/issues/130). The names, the transcripts, the README, and "Moving to kodor" are in the ticket's "Proposed docs".

### What and why

The owner has bought the domain kodor.ai and is renaming the product from "software factory" to Kodor. This ticket carries the new name through everything a user or a contributor reads, so nothing says "software factory" where it means the product.

#### What it covers

- The product's name wherever it is said: `README.md`, every page under `docs/`, the text of the skills, agents, rules, and review instructions, and what the commands print, such as `✓ Opened acme/web#41, "Set up the software factory"`.
- The docs' home: the site #126 builds is served at https://kodor.ai.

#### Moving the board

When the repository moves to `kodor-ai`, the board moves with it, and no issue is moved by hand: the board sync adds every open ticket with the factory's label, `factory` before the rename and `kodor` after, to a board that lacks it, in the column its markers call for.

1. Transfer the repository to `kodor-ai` and rename it `kodor`, so it is `kodor-ai/kodor` (Settings, General, Transfer ownership, then Repository name). Its issues, pull requests, and labels go with it. Check that its Actions secrets came across, and point local clones at the new address.
2. The new board is https://github.com/orgs/kodor-ai/projects/1 ("kodor.ai"), which the owner created on 2026-11-27. Its Status columns and its Cost, `Session`, and `Runs in` fields match the old board's. Its Priority field has no options yet, where the old board's are P0, P1, and P2. Its `Spec` and `Builder notes` fields are the owner's: the factory writes neither.
3. `tickets.board` in `.claude/factory.yaml` stays `1`: once the repository is in `kodor-ai`, board 1 is that organization's.
4. Replace the `FACTORY_BOARD_TOKEN` secret with a token that can write projects in `kodor-ai`.
5. Preview with `npx --no-install factory board --dry-run`: each ticket should print `added to the board; set Status, …`, and a missing column or field prints `no such column on the board` or `skipped: no such field`.
6. Run the sync with `gh workflow run factory.yml -f job=board` rather than waiting for its nightly run.
7. Remove this repository's cards from the old board, https://github.com/users/davidbyoung/projects/1, which the repository the factory was drawn out of keeps using: filter its view to this repository, select all, and delete them from the project, which leaves the issues alone.

What the sync cannot rebuild, set again by hand on the new board: a card the owner moved to Ready, a worked ticket the owner moved back to Backlog, the Priority values, the cards' order, and closed tickets older than the 30 most recently closed, which stay on the old board.

### Decisions

- Opened on 2026-11-27 at the owner's request, while #126 was updated to host the site at kodor.ai.
- #130 waits on #125: #125's body has the README and three overview pages written out under the old name, and moves every page, so renaming first would mean redoing both.
- **The npm package is `@kodor-ai/kodor`,** published to the owner's npm organization `kodor-ai`, so a user installs the command once with `npm install -g @kodor-ai/kodor`, as the docs install it, and then runs `kodor init`. Decided by the owner on 2026-11-27. It replaces `@davidbyoung/software-factory`, which is deprecated with a message naming the new package rather than unpublished. The release workflow changes with it: `release.yml` checks the version against `@davidbyoung%2fsoftware-factory` on the registry, and its trusted publisher is set on the old package's page. A trusted publisher is set on a package that exists, so the first release of `@kodor-ai/kodor` publishes with the `NPM_TOKEN` fallback the workflow already has, a granular token allowed to publish in the `kodor-ai` organization, and the trusted publisher is set on the new package's page after. The repository has no `NPM_TOKEN` secret yet, so the owner creates one before the first release. npm sets a trusted publisher made now to stage releases only, so the owner chooses "allow npm publish" when setting it, and since a new one expires unless it publishes within 2 days, sets it right before the second release. `package.json`'s `repository.url` becomes `git+https://github.com/kodor-ai/kodor.git`, which a trusted publish must match exactly. (Q9 and Q10 under Proposed docs.)
- **What `factory init --org` sets up in an organization takes the new name,** decided by the owner on 2026-11-27. Each is fixed in `src/init-org.mts` today:
  - The repository that holds the organization's preset and poller, `factory-config` (`CONFIG`), becomes `kodor-config`, so a repository's preset list names `ORG/kodor-config`, such as `kodor-ai/kodor-config//node`.
  - The custom property set to `on` for each repository set up with the factory, `software-factory` (`PROPERTY`), becomes `kodor`.
  - The title of the board it creates, "Software factory" (`BOARD_TITLE`), becomes "kodor", lowercase as the name always is.
- **The names a user types and sets,** decided by the owner on 2026-11-27:
  - The command is `kodor`, as in `kodor init` and `npx --no-install kodor gate`.
  - The label on every ticket the factory works on is `kodor`. A repository moving over renames its label on GitHub, which keeps it on every issue.
  - `FACTORY_*` becomes `KODOR_*`: the secrets, the variables such as `FACTORY_APP_CLIENT_ID`, and the variables the workflows set for themselves. GitHub can neither rename nor reveal a secret, so a repository moving over creates each secret again under its new name.
  - The GitHub App that `factory init --org` registers for an organization is `kodor-ORG`, lowercase, such as `kodor-acme`, shown as `kodor-acme[bot]`. It cannot be `kodor` alone: each organization registers its own App, and an App's name is unique across GitHub. Today `appName` in `src/code-host/github.mts` makes "Software Factory for ORG".
  - The settings files stay under `.claude/`: `.claude/factory.yaml`, `.claude/factory.lock`, and `.claude/factory.choices.yaml` become `.claude/kodor.yaml`, `.claude/kodor.lock`, and `.claude/kodor.choices.yaml`, and the `.claude/factory/` folder becomes `.claude/kodor/`.
  - "Software factory" stays as a description, as in "Kodor, a software factory for your coding agent".
- **The repository moves to `kodor-ai/kodor`, and its board with it,** decided by the owner on 2026-11-27, as part of this ticket. The factory reads the board under the repository's owner, and `.claude/factory.yaml` has no setting for a different owner, so the board in `kodor-ai` works only once the repository is there. "Moving the board" above is how.
- **The skills and agents take the `kodor-` prefix,** as in `/kodor-refine`, `/kodor-build`, and `kodor-test-reviewer`, decided by the owner on 2026-11-27, as part of this ticket. They are copied into a user's own `.claude/skills/` and `.claude/agents/`, beside the user's own and Claude Code's built-in ones, so they keep a prefix, and typing `/kodor` lists the skills.
- **The workflows become `kodor.yml` and `kodor-review.yml`,** from `factory.yml` and `factory-review.yml`, decided by the owner on 2026-11-27. A check whose name carries the old one changes with it, and a ruleset that requires the check by name is updated in the same move, or every pull request waits on a check that no longer runs: this repository's ruleset requires `review / Factory files in step`.

- **"The factory" becomes "kodor" too,** wherever it means the product: in prose, in what the commands print, and in the skills and rules, as in "Downloading kodor 0.3.0, which this repository names." Approved by the owner on 2026-11-27 (Q1).
- **The checks become `kodor / …` and `review / kodor files in step`:** the workflows' job id `factory` becomes `kodor`, and the job "Factory files in step" becomes "kodor files in step". The workflows' titles become `kodor` and `kodor review`. Approved by the owner on 2026-11-27 (Q2).
- **The addresses a command prints point at `kodor-ai/kodor` on GitHub,** at the installed version's tag, as `docsPage` makes them today. Pointing them at https://kodor.ai stays with #126. Approved by the owner on 2026-11-27 (Q5).
- **A repository not moved yet gets a failing update job,** accepted by the owner on 2026-11-27 (Q6). Its job finds kodor's release through GitHub's redirect and cannot download it from the old package. The upgrade note "Moving to kodor" names the symptom. There is no `factory` alias and no migration code: two repositories use the factory, and the other is on 0.1.5 with workflow files of its own, so it calls none of this repository's.
- **The upgrade note covers a repository, not an organization,** since none has been set up with `factory init --org`. Approved by the owner on 2026-11-27 (Q7).
- **Three folders outside the repository carry the old name,** not two: `~/.cache/software-factory/`, `~/.local/share/software-factory/work`, and `~/.config/software-factory/credentials.yaml`, which become `~/.cache/kodor/`, `~/.local/share/kodor/work`, and `~/.config/kodor/credentials.yaml`. The credentials file holds tokens, so the note moves it rather than deleting it, and the credentials guard watches the new path. Approved by the owner on 2026-11-27 (Q8).
- **The README becomes a short page:** what kodor is, how to install it, and links to https://kodor.ai, its quick start, and "Moving to kodor". It replaces the spec line "The README routes" from #125. #130 does not wait on #126: its kodor.ai links do not work until #126 puts the site up, which the owner accepted on 2026-11-27 (Q11). #126's line "The README links to the site" is then met by #130.
- **The repository moved to `kodor-ai/kodor` on 2026-11-27,** before refinement finished, and its clone points there.

- **A moving repository's old hooks are deleted by hand,** decided by the owner on 2026-11-27 in refinement. `kodor sync` recognizes its own hooks by `kodor` and `bin/kodor.js` only, so the upgrade note has a step that deletes each hook running `factory`, and `~/.local/share/software-factory/work`, from `.claude/settings.json`. No code knows the old names. For this repository, whose hooks run `bin/factory.js`, the build changes each to `bin/kodor.js` by hand (task 2.2), and deletes the old work folder and import line after its sync (task 7.3).
- **The settings version starts again at 1,** decided by the owner on 2026-11-27, as part of this ticket and its pull request. `.claude/kodor.yaml` says `version: 1`, the shape it has today as `version: 2`, and kodor accepts no other. A file that still says `version: 2` is told to see "Moving to kodor", whose step 3 changes the line, as the old version 1 was told to see "Moving to settings version 2". That older section keeps its numbers, since it describes `.claude/factory.yaml` before the rename.
- **Marker comments and git refs keep their text,** a technical call made in refinement on 2026-11-27: `<!-- factory: ticket KEY -->`, `<!-- factory: follow-ups -->`, `<!-- factory: cloud-build -->`, `<!-- factory: owner-marks-ready -->`, `<!-- factory-deps -->`, `<!-- factory: approval policies wait for the label -->`, and `refs/factory/base` and `refs/factory/head`. Only kodor reads them, no reader sees them rendered, and open tickets and pull requests already carry them, so renaming them would take the migration code the ticket rules out.
- **A preset's file becomes `kodor-preset.yaml`, and an organization's poller file `.github/workflows/kodor-poller.yml`,** a technical call made in refinement on 2026-11-27, since each is a file a user writes or reads, as the settings files are. No preset or organization uses either yet. The `User-Agent` kodor sends becomes `kodor`, and the website review's folder in a user's repository, `node_modules/.cache/factory/site/` (`src/site.mts`, `src/site/servers.mts`, `docs/features/website-review.md`), becomes `node_modules/.cache/kodor/site/`: it is a cache, so nothing moves.
- **The specs are renamed in place,** a technical call made in refinement on 2026-11-27. 69 of the specs under `openspec/specs/` quote an old name, so a delta line for each would restate behavior that does not change. The build rewrites the names in `openspec/specs/` directly, renames the capability `factory-label` to `kodor-label`, and the Spec below holds only the lines whose behavior changes beyond the rename.
- **The upgrade notes below "Moving to kodor" keep the names of their releases,** a technical call made in refinement on 2026-11-27. A repository on an old release takes them oldest first, with the `factory` command it still has, and "Moving to kodor" last.
- **No build order.** #130 waits on no open ticket. #63 (Jira) and #126 (the site) touch the same files, which is a merge conflict, not a blocker. #63's body names `FACTORY_JIRA_EMAIL` and `FACTORY_JIRA_TOKEN`: whichever of the two builds second uses the names in effect then, and the product-name test in Spec line 1 fails a build that adds an old one.
